## 1. 通用约定

### 1.1 统一返回体

所有接口返回（`CLAUDE.md` 规定）：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

### 1.2 错误码

| code | 含义 | 说明 |
|---|---|---|
| 200 | 成功 | |
| 400 | 参数错误 | 校验失败，`msg` 说明具体字段 |
| 401 | 未登录 / token 失效 | 前端应跳转登录页 |
| 403 | 无权限 | 试图访问他人资源 |
| 404 | 资源不存在 | |
| 500 | 业务异常 | `msg` 为可展示给用户的提示 |

### 1.3 分页

**请求参数**（`CLAUDE.md` 规定）：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pageNum` | int | 1 | 页码，从 1 开始 |
| `pageSize` | int | 10 | 每页条数 |

**响应 `data` 结构**：

```json
{
  "total": 100,
  "pageNum": 1,
  "pageSize": 10,
  "records": []
}
```

### 1.4 认证

- 除注册、登录外，**所有接口都需要登录**
- token 放在请求头：`Authorization: Bearer <token>`
- 前端用 axios 请求拦截器统一注入，**禁止每个接口手写**（`CLAUDE.md` 规定）

### 1.5 日期格式（统一，不许各写各的）

| 类型 | 格式 | 示例 |
|---|---|---|
| 日期 | `yyyy-MM-dd` | `2026-09-18` |
| 日期时间 | `yyyy-MM-dd HH:mm:ss` | `2026-09-18 14:30:00` |

**不使用时间戳。** 前后端都按此格式序列化。

### 1.6 ⚠️ 安全铁律

**所有带 `user_id` 的表，任何查询都必须限定当前用户。**

后端从 token 解析出当前用户 id，**由 MyBatis-Plus 拦截器统一注入条件**，Controller 和 Service 都不手写 `user_id` 过滤——手写迟早会漏，漏一次就是数据泄露。

## 3. 认证 `/api/auth`

| 方法 | 路径 | 说明 | 需登录 |
|---|---|---|---|
| POST | `/api/auth/register` | 注册 | ❌ |
| POST | `/api/auth/login` | 登录 | ❌ |
| GET | `/api/auth/me` | 获取当前登录用户信息 | ✅ |

> **登出不需要接口**：token 由前端丢弃即可。若将来改用服务端 token 存储再加。

### POST `/api/auth/register`

**入参**

```json
{ "username": "zhangsan", "password": "123456", "nickname": "张三" }
```

**校验规则**：`username` 4-50 位字母数字下划线、唯一；`password` 6-32 位；`nickname` 可空，默认取 `username`。

**出参** `data`：`null`

### POST `/api/auth/login`

**入参**

```json
{ "username": "zhangsan", "password": "123456" }
```

**出参** `data`

```json
{
  "token": "eyJhbGciOi...",
  "userInfo": { "id": 1, "username": "zhangsan", "nickname": "张三", "avatar": "" }
}
```

**注意**：`userInfo` **不包含 password 字段**。`CLAUDE.md` 明确规定"禁止直接把 Entity 返回前端"。

### GET `/api/auth/me`

返回当前登录用户信息，结构同上面的 `userInfo`。

## 4. 每日计划 `/api/plan-task`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/plan-task` | 查某天的任务列表 |
| GET | `/api/plan-task/range` | 查日期范围的任务（6 个月内） |
| POST | `/api/plan-task` | 新增任务 |
| PUT | `/api/plan-task/{id}` | 修改任务内容 |
| PATCH | `/api/plan-task/{id}/completed` | 切换完成状态 |
| DELETE | `/api/plan-task/{id}` | 删除任务 |

### GET `/api/plan-task?date=2026-09-18`

**出参** `data`：任务数组（**不分页**，一天的任务量很小）

```json
[
  { "id": 1, "planDate": "2026-09-18", "content": "喝水量", "completed": 1, "completedTime": "2026-09-18 09:00:00", "sortOrder": 0 },
  { "id": 2, "planDate": "2026-09-18", "content": "刷题", "completed": 0, "completedTime": null, "sortOrder": 1 }
]
```

### GET `/api/plan-task/range?startDate=&endDate=`

**约束**：`endDate - startDate` **不得超过 6 个月**，超出返回 `400`。这是需求里"可查看 6 个月内"的落地方式。

### PATCH `/api/plan-task/{id}/completed`

**入参**

```json
{ "completed": 1 }
```

**为什么用 PATCH 而不是 PUT**：勾选只需改一个字段，`PUT` 语义是全量更新，用在这里不合适（`CLAUDE.md` 的 RESTful 约定）。

后端自动维护 `completed_time`：标记完成时写入当前时间，取消完成时置 `null`。

## 5. 生日与纪念日 `/api/anniversary`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/anniversary` | 全部列表 |
| GET | `/api/anniversary/upcoming` | 即将到来的（首页提醒用） |
| POST | `/api/anniversary` | 新增 |
| PUT | `/api/anniversary/{id}` | 修改 |
| DELETE | `/api/anniversary/{id}` | 删除 |

### 实体结构

```json
{
  "id": 1,
  "name": "妈妈",
  "type": 1,
  "relation": "家人",
  "month": 10,
  "day": 5,
  "remindDays": 7,
  "remark": ""
}
```

`type`：`1` 生日 / `2` 纪念日

### GET `/api/anniversary/upcoming`

**出参** `data`

```json
[
  { "id": 1, "name": "妈妈", "type": 1, "relation": "家人", "month": 10, "day": 5, "daysUntil": 3, "nextDate": "2026-10-05" }
]
```

**返回规则**：`daysUntil <= remindDays` 的记录。**`daysUntil` 和 `nextDate` 由后端计算**——因为生日只存月日，跨年推算（今天 12 月，生日在 1 月）在 SQL 里做不了，必须用 Java 算（见数据模型 §4.3）。

前端**不要自己算**，直接用这两个字段。

## 6. 备忘录 `/api/memo`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/memo` | 分页列表（支持搜索） |
| GET | `/api/memo/{id}` | 详情 |
| POST | `/api/memo` | 新增 |
| PUT | `/api/memo/{id}` | 修改 |
| DELETE | `/api/memo/{id}` | 删除 |

### GET `/api/memo`

分页列表，可按关键词搜索。

**入参**（查询参数，全部可选）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pageNum` | int | 1 | 页码，小于 1 按 1 处理 |
| `pageSize` | int | 10 | 每页条数，上限 100；`<= 0` 回落到默认值 |
| `keyword` | string | 无 | 对 `title` 和 `content` 模糊匹配；超过 50 字截断 |

**排序**：`updateTime` 倒序，同值再按 `id` 倒序。第二级排序不能省——时间只精确到秒，同一秒内建的几条若无稳定次序，翻页时会出现同一条忽而在第 2 页忽而在第 3 页。

**出参** `data`（分页结构见 §1.3）

```json
{
  "total": 23,
  "pageNum": 1,
  "pageSize": 10,
  "records": [
    { "id": 12, "title": "周会要点", "summary": "1. 排期确认…", "updateTime": "2026-09-19 23:45:01" }
  ]
}
```

**列表不返回 `content`**（正文可能很长、上限 15000 字，列表页用不上），只给 `summary`——正文压成单行后的前 60 个码点，超出部分以 `…` 结尾。这是典型的 VO 拆分，避免列表接口传一堆用不上的数据。

`title` 可能为空串（标题与正文至少写一个即可，见下）；正文为空时 `summary` 也为空串。

### GET `/api/memo/{id}`

**出参** `data`

```json
{
  "id": 12,
  "title": "周会要点",
  "content": "1. 排期确认\n2. ……",
  "createTime": "2026-09-19 23:45:01",
  "updateTime": "2026-09-19 23:45:01"
}
```

### POST `/api/memo` · PUT `/api/memo/{id}`

**入参** `application/json`

```json
{ "title": "周会要点", "content": "1. 排期确认" }
```

| 字段 | 约束 |
|---|---|
| `title` | 可空，≤ 100 字 |
| `content` | 可空，≤ 15000 字（`TEXT` 列 65535 字节，utf8mb4 下一字符最多 4 字节，故留有余量） |

**`title` 与 `content` 不能同时为空**（400）。不同时强制标题非空，是因为随手记一笔往往就是一段话，强制先起标题会让人干脆不记了。

**出参** `data`：同详情。新增与修改都返回完整详情，前端保存完可直接用返回值刷新，不必再发一次 GET。

> 时间字段是**数据库**填的（`DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`），写接口在返回前会重新查一次，确保 `createTime` / `updateTime` 非空且是本次写入后的值。

### DELETE `/api/memo/{id}`

**出参** `data`: `null`。逻辑删除。

### 通用返回约定

- 未查到、或该 id 存在但不属于当前用户，**一律 404**（不返回 403——403 等于确认该 id 存在，而主键连续自增，这就成了存在性探测点）
- 搜索的 `keyword` **未转义 LIKE 通配符**：搜 `%` 会命中自己的全部记录。隔离不受影响（看到的仍是自己的），按已知行为处理

## 7. 首页聚合 `/api/dashboard`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/dashboard` | 一次返回首页需要的全部数据 |

**入参**：无。返回的永远是**当前登录用户**的那一份——这个接口的"资源"就是登录态本身。

**出参** `data`

```json
{
  "todayPlan": {
    "total": 5,
    "completed": 2,
    "tasks": [
      { "id": 12, "planDate": "2026-09-19", "content": "写周报", "completed": 1,
        "completedTime": "2026-09-19 10:03:00", "sortOrder": 0 }
    ]
  },
  "upcomingAnniversaries": [
    { "id": 3, "name": "妈妈", "type": 1, "relation": "家人",
      "month": 10, "day": 5, "daysUntil": 3, "nextDate": "2026-10-05" }
  ],
  "memoCount": 12
}
```

| 字段 | 说明 |
|---|---|
| `todayPlan.tasks` | **今天**的任务，结构与 `GET /api/plan-task` 的 `PlanTaskVO` 完全一致，顺序也一致（`sortOrder`、`id` 升序）。昨天和明天的不在其中 |
| `todayPlan.total` / `completed` | `tasks` 的派生值。同时也是列表长度和 `completed === 1` 的条数——**三个数由同一个入参推导**，不会出现"列表 5 条、分母写着 4" |
| `upcomingAnniversaries` | 与 `GET /api/anniversary/upcoming` **同结构、同排序**（剩余天数升序）。前端可以直接交给首页那个组件渲染 |
| `memoCount` | 备忘总条数，已逻辑删除的不计。只用于卡片上显示一个数字 |

**空账号**：全部为 `0` / 空数组，不返回 `null`，也不报错——这是新用户首次登录时唯一会走到的分支。

**为什么要这个聚合接口**：首页要同时显示今日任务 + 生日提醒 + 备忘条数，如果分成 3 个请求，页面加载慢且前端要处理多个 loading 状态。聚合成一个接口更实用。

**为什么 `todayPlan.tasks` 直接复用 `PlanTaskVO`**：另建一个"首页专用"结构就会有两份实现，`daysUntil` 那样"由后端算好"的口径也会跟着分叉。后端这三个字段分别调 `PlanTaskService` / `AnniversaryService` / `MemoService` 的现成方法，**不自己拼 SQL**——聚合一层的价值在于少两次 HTTP 往返，不在于多一次查询实现。

> 注：这不算严格的 RESTful 资源接口，是实用的聚合端点。`CLAUDE.md` 的规范针对资源 CRUD，聚合端点不冲突。

## 8. 新闻 `/api/news`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/news` | 当日新闻列表 |

**出参** `data`：新闻数组，取自 `wb_news` 表中 `fetch_date = 今天` 的记录，**按 `publish_time` 倒序**。

**⚠️ 后端定时任务**：每小时从聚合数据拉取一次写入 `wb_news`，用户请求只读数据库。

**绝不能**在用户请求时实时调第三方接口——几十个用户刷新几次，配额就没了。

若当天无数据（定时任务失败等），返回空数组，**不报错**——首页少一块内容，好过整页打不开。

## 11. 课程 `/api/course`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/course` | 查某学期的课程（课表数据） |
| POST | `/api/course` | 新增 |
| PUT | `/api/course/{id}` | 修改 |
| DELETE | `/api/course/{id}` | 删除 |

### GET `/api/course?semesterId=1`

**出参** `data`：课程数组（**不分页**，一个学期的课就几十条）

```json
[
  {
    "id": 1, "semesterId": 1, "name": "高等数学", "teacher": "李老师", "location": "教三 201",
    "dayOfWeek": 1, "startSection": 2, "endSection": 3,
```

- 具体每节几点几分也由前端决定，接口不返回
- `weekType`：`0` 每周 / `1` 单周 / `2` 双周

## 12. 已确认事项

**1. 删除学期时，其下课程的处理 —— 采用 B 方案：禁止删除**

有课程关联时，`DELETE /api/semester/{id}` 返回 `400`，`msg` 提示"请先删除该学期下的课程"。

**选择理由**：学期是低频操作，多一步确认成本很低；而级联删除一旦误操作，用户的课程数据不可逆丢失。

**2. 注册开关 —— 加**

配置项 `workbench.registration.enabled`，默认 `true`。关闭后 `POST /api/auth/register` 返回 `403`。

**理由**：定位是"主要自己用，顺便让别人用"。默认开放，需要时改配置关掉即可，不必改代码。
