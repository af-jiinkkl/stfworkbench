## 1. 通用约定

### 1.1 统一返回体

所有接口返回（`CLAUDE.md` 规定）：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

### 1.2 错误码

| code | 含义 | 说明 |
|---|---|---|
| 200 | 成功 | |
| 400 | 参数错误 | 校验失败，`msg` 说明具体字段 |
| 401 | 未登录 / token 失效 | 前端应跳转登录页 |
| 403 | 无权限 | 试图访问他人资源 |
| 404 | 资源不存在 | |
| 500 | 业务异常 | `msg` 为可展示给用户的提示 |

### 1.3 分页

**请求参数**（`CLAUDE.md` 规定）：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pageNum` | int | 1 | 页码，从 1 开始 |
| `pageSize` | int | 10 | 每页条数 |

**响应 `data` 结构**：

```json
{
  "total": 100,
  "pageNum": 1,
  "pageSize": 10,
  "records": []
}
```

### 1.4 认证

- 除注册、登录外，**所有接口都需要登录**
- token 放在请求头：`Authorization: Bearer <token>`
- 前端用 axios 请求拦截器统一注入，**禁止每个接口手写**（`CLAUDE.md` 规定）

### 1.5 日期格式（统一，不许各写各的）

| 类型 | 格式 | 示例 |
|---|---|---|
| 日期 | `yyyy-MM-dd` | `2026-09-18` |
| 日期时间 | `yyyy-MM-dd HH:mm:ss` | `2026-09-18 14:30:00` |

**不使用时间戳。** 前后端都按此格式序列化。

### 1.6 ⚠️ 安全铁律

**所有带 `user_id` 的表，任何查询都必须限定当前用户。**

后端从 token 解析出当前用户 id，**由 MyBatis-Plus 拦截器统一注入条件**，Controller 和 Service 都不手写 `user_id` 过滤——手写迟早会漏，漏一次就是数据泄露。

## 3. 认证 `/api/auth`

| 方法 | 路径 | 说明 | 需登录 |
|---|---|---|---|
| POST | `/api/auth/register` | 注册 | ❌ |
| POST | `/api/auth/login` | 登录 | ❌ |
| GET | `/api/auth/me` | 获取当前登录用户信息 | ✅ |

> **登出不需要接口**：token 由前端丢弃即可。若将来改用服务端 token 存储再加。

### POST `/api/auth/register`

**入参**

```json
{ "username": "zhangsan", "password": "123456", "nickname": "张三" }
```

**校验规则**：`username` 4-50 位字母数字下划线、唯一；`password` 6-32 位；`nickname` 可空，默认取 `username`。

**出参** `data`：`null`

### POST `/api/auth/login`

**入参**

```json
{ "username": "zhangsan", "password": "123456" }
```

**出参** `data`

```json
{
  "token": "eyJhbGciOi...",
  "userInfo": { "id": 1, "username": "zhangsan", "nickname": "张三", "avatar": "" }
}
```

**注意**：`userInfo` **不包含 password 字段**。`CLAUDE.md` 明确规定"禁止直接把 Entity 返回前端"。

### GET `/api/auth/me`

返回当前登录用户信息，结构同上面的 `userInfo`。

## 4. 每日计划 `/api/plan-task`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/plan-task` | 查某天的任务列表 |
| GET | `/api/plan-task/range` | 查日期范围的任务（6 个月内） |
| POST | `/api/plan-task` | 新增任务 |
| PUT | `/api/plan-task/{id}` | 修改任务内容 |
| PATCH | `/api/plan-task/{id}/completed` | 切换完成状态 |
| DELETE | `/api/plan-task/{id}` | 删除任务 |

### GET `/api/plan-task?date=2026-09-18`

**出参** `data`：任务数组（**不分页**，一天的任务量很小）

```json
[
  { "id": 1, "planDate": "2026-09-18", "content": "喝水量", "completed": 1, "completedTime": "2026-09-18 09:00:00", "sortOrder": 0 },
  { "id": 2, "planDate": "2026-09-18", "content": "刷题", "completed": 0, "completedTime": null, "sortOrder": 1 }
]
```

### GET `/api/plan-task/range?startDate=&endDate=`

**约束**：`endDate - startDate` **不得超过 6 个月**，超出返回 `400`。这是需求里"可查看 6 个月内"的落地方式。

### PATCH `/api/plan-task/{id}/completed`

**入参**

```json
{ "completed": 1 }
```

**为什么用 PATCH 而不是 PUT**：勾选只需改一个字段，`PUT` 语义是全量更新，用在这里不合适（`CLAUDE.md` 的 RESTful 约定）。

后端自动维护 `completed_time`：标记完成时写入当前时间，取消完成时置 `null`。

## 5. 生日与纪念日 `/api/anniversary`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/anniversary` | 全部列表 |
| GET | `/api/anniversary/upcoming` | 即将到来的（首页提醒用） |
| POST | `/api/anniversary` | 新增 |
| PUT | `/api/anniversary/{id}` | 修改 |
| DELETE | `/api/anniversary/{id}` | 删除 |

### 实体结构

```json
{
  "id": 1,
  "name": "妈妈",
  "type": 1,
  "relation": "家人",
  "month": 10,
  "day": 5,
  "remindDays": 7,
  "remark": ""
}
```

`type`：`1` 生日 / `2` 纪念日

### GET `/api/anniversary/upcoming`

**出参** `data`

```json
[
  { "id": 1, "name": "妈妈", "type": 1, "relation": "家人", "month": 10, "day": 5, "daysUntil": 3, "nextDate": "2026-10-05" }
]
```

**返回规则**：`daysUntil <= remindDays` 的记录。**`daysUntil` 和 `nextDate` 由后端计算**——因为生日只存月日，跨年推算（今天 12 月，生日在 1 月）在 SQL 里做不了，必须用 Java 算（见数据模型 §4.3）。

前端**不要自己算**，直接用这两个字段。

## 6. 备忘录 `/api/memo`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/memo` | 分页列表（支持搜索） |
| GET | `/api/memo/{id}` | 详情 |
| POST | `/api/memo` | 新增 |
| PUT | `/api/memo/{id}` | 修改 |
| DELETE | `/api/memo/{id}` | 删除 |

### GET `/api/memo`

分页列表，可按关键词搜索。

**入参**（查询参数，全部可选）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pageNum` | int | 1 | 页码，小于 1 按 1 处理 |
| `pageSize` | int | 10 | 每页条数，上限 100；`<= 0` 回落到默认值 |
| `keyword` | string | 无 | 对 `title` 和 `content` 模糊匹配；超过 50 字截断 |

**排序**：`updateTime` 倒序，同值再按 `id` 倒序。第二级排序不能省——时间只精确到秒，同一秒内建的几条若无稳定次序，翻页时会出现同一条忽而在第 2 页忽而在第 3 页。

**出参** `data`（分页结构见 §1.3）

```json
{
  "total": 23,
  "pageNum": 1,
  "pageSize": 10,
  "records": [
    { "id": 12, "title": "周会要点", "summary": "1. 排期确认…", "updateTime": "2026-09-19 23:45:01" }
  ]
}
```

**列表不返回 `content`**（正文可能很长、上限 15000 字，列表页用不上），只给 `summary`——正文压成单行后的前 60 个码点，超出部分以 `…` 结尾。这是典型的 VO 拆分，避免列表接口传一堆用不上的数据。

`title` 可能为空串（标题与正文至少写一个即可，见下）；正文为空时 `summary` 也为空串。

### GET `/api/memo/{id}`

**出参** `data`

```json
{
  "id": 12,
  "title": "周会要点",
  "content": "1. 排期确认\n2. ……",
  "createTime": "2026-09-19 23:45:01",
  "updateTime": "2026-09-19 23:45:01"
}
```

### POST `/api/memo` · PUT `/api/memo/{id}`

**入参** `application/json`

```json
{ "title": "周会要点", "content": "1. 排期确认" }
```

| 字段 | 约束 |
|---|---|
| `title` | 可空，≤ 100 字 |
| `content` | 可空，≤ 15000 字（`TEXT` 列 65535 字节，utf8mb4 下一字符最多 4 字节，故留有余量） |

**`title` 与 `content` 不能同时为空**（400）。不同时强制标题非空，是因为随手记一笔往往就是一段话，强制先起标题会让人干脆不记了。

**出参** `data`：同详情。新增与修改都返回完整详情，前端保存完可直接用返回值刷新，不必再发一次 GET。

> 时间字段是**数据库**填的（`DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`），写接口在返回前会重新查一次，确保 `createTime` / `updateTime` 非空且是本次写入后的值。

### DELETE `/api/memo/{id}`

**出参** `data`: `null`。逻辑删除。

### 通用返回约定

- 未查到、或该 id 存在但不属于当前用户，**一律 404**（不返回 403——403 等于确认该 id 存在，而主键连续自增，这就成了存在性探测点）
- 搜索的 `keyword` **未转义 LIKE 通配符**：搜 `%` 会命中自己的全部记录。隔离不受影响（看到的仍是自己的），按已知行为处理

## 7. 首页聚合 `/api/dashboard`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/dashboard` | 一次返回首页需要的全部数据 |

**入参**：无。返回的永远是**当前登录用户**的那一份——这个接口的"资源"就是登录态本身。

**出参** `data`

```json
{
  "todayPlan": {
    "total": 5,
    "completed": 2,
    "tasks": [
      { "id": 12, "planDate": "2026-09-19", "content": "写周报", "completed": 1,
        "completedTime": "2026-09-19 10:03:00", "sortOrder": 0 }
    ]
  },
  "upcomingAnniversaries": [
    { "id": 3, "name": "妈妈", "type": 1, "relation": "家人",
      "month": 10, "day": 5, "daysUntil": 3, "nextDate": "2026-10-05" }
  ],
  "memoCount": 12,
  "todayExpenseAmount": 40.50
}
```

| 字段 | 说明 |
|---|---|
| `todayPlan.tasks` | **今天**的任务，结构与 `GET /api/plan-task` 的 `PlanTaskVO` 完全一致，顺序也一致（`sortOrder`、`id` 升序）。昨天和明天的不在其中 |
| `todayPlan.total` / `completed` | `tasks` 的派生值。同时也是列表长度和 `completed === 1` 的条数——**三个数由同一个入参推导**，不会出现"列表 5 条、分母写着 4" |
| `upcomingAnniversaries` | 与 `GET /api/anniversary/upcoming` **同结构、同排序**（剩余天数升序）。前端可以直接交给首页那个组件渲染 |
| `memoCount` | 备忘总条数，已逻辑删除的不计。只用于卡片上显示一个数字 |
| `todayExpenseAmount` | **今天**的消费合计（不是本月、不是全部）。没有记录时是 `0.00`，**不是 `null`** |

**空账号**：全部为 `0` / 空数组 / `0.00`，不返回 `null`，也不报错——这是新用户首次登录时唯一会走到的分支。

**为什么要这个聚合接口**：首页要同时显示今日任务 + 生日提醒 + 备忘条数 + 今日消费，如果分成 4 个请求，页面加载慢且前端要处理多个 loading 状态。聚合成一个接口更实用。

**为什么 `todayPlan.tasks` 直接复用 `PlanTaskVO`**：另建一个"首页专用"结构就会有两份实现，`daysUntil` 那样"由后端算好"的口径也会跟着分叉。后端这几个字段分别调 `PlanTaskService` / `AnniversaryService` / `MemoService` / `ExpenseService` 的现成方法，**不自己拼 SQL**——聚合一层的价值在于少几次 HTTP 往返，不在于多一次查询实现。

**`todayExpenseAmount` 为什么不是 `0` 而是 `0.00`**：它走的是 `ExpenseService#sumOf(today, today)`，空区间下取的是 `reduce` 的初值常量。若改成"从数据库 `SUM` 出来再兜底"，很容易写出一个刻度为 0 的 `BigDecimal.ZERO`，前端拿到就会显示成"¥0"而不是"¥0.00"——而这只在**新账号**上出现，开发时几乎看不到。`DashboardServiceTest#emptyUserGetsZeroes` 专门钉了这一条。

**`todayExpenseAmount` 为什么是 JSON number**：后端 `BigDecimal` 由 Jackson 默认序列化成数字。`DECIMAL(10,2)` 的取值范围（最大 `99999999.99`）远在 double 能精确表示整数的 2^53 之内，且前端只显示不参与求和，所以不做字符串化。前端显示前走 `utils/money.ts`。

> 注：这不算严格的 RESTful 资源接口，是实用的聚合端点。`CLAUDE.md` 的规范针对资源 CRUD，聚合端点不冲突。

## 8. 新闻 `/api/news`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/news` | 当日新闻列表 |

**出参** `data`：新闻数组，取自 `wb_news` 表中 `fetch_date = 今天` 的记录，**按 `publish_time` 倒序**。

## 9. 消费 `/api/expense`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/expense` | 分页列表（可按日期、分类筛选） |
| GET | `/api/expense/{id}` | 详情 |
| POST | `/api/expense` | 新增 |
| PUT | `/api/expense/{id}` | 修改 |
| DELETE | `/api/expense/{id}` | 删除 |
| GET | `/api/expense/summary/category` | 按分类统计（饼图） |
| GET | `/api/expense/summary/month` | 按月趋势（折线图） |

### 通用：金额与日期

| 项 | 约定 |
|---|---|
| 金额存储 | `DECIMAL(10,2)`，最大 `99999999.99`。**绝不用 FLOAT/DOUBLE** |
| 金额传输 | JSON **number**（后端 `BigDecimal` 的默认序列化）。显示前由前端格式化成两位小数 |
| 入参校验 | `@DecimalMin("0.01")` + `@Digits(integer=8, fraction=2)`，两位小数、必须是正数 |
| 日期 | `yyyy-MM-dd`，见 §1.5。**`expenseDate` 是消费发生的那天，与创建时间无关**，允许补录过去、也允许填将来 |

### GET `/api/expense?pageNum=&pageSize=&startDate=&endDate=&category=`

分页列表，三个筛选参数全部可选。返回 `PageResult<ExpenseVO>`。

| 参数 | 说明 |
|---|---|
| `pageNum` / `pageSize` | `pageNum` 小于 1 按 **1** 处理；`pageSize` 不传或小于等于 0 按 **10** 处理，上限 **100**。三个数字都由后端夹，不依赖 MyBatis-Plus 的容错 |
| `startDate` / `endDate` | **闭区间**（含首含尾）。`startDate` 晚于 `endDate` 返回 `400` |
| `category` | 分类名。**非法分类不报错，按"查不到"处理**——它是筛选条件不是待写库的值 |

**排序**：`expense_date` 降序，同一天按 `id` 降序。固定，不可由前端指定。

**出参** `records[]`

```json
{
  "id": 12,
  "amount": 12.50,
  "category": "餐饮",
  "expenseDate": "2026-09-21",
  "remark": "午饭",
  "createTime": "2026-09-21 12:03:11",
  "updateTime": "2026-09-21 12:03:11"
}
```

`remark` 没填时是**空串**而非 `null`。

### GET `/api/expense/{id}` · POST `/api/expense` · PUT `/api/expense/{id}` · DELETE `/api/expense/{id}`

详情 / 新增 / 全量替换 / 逻辑删除。出参与上面的 `ExpenseVO` **完全一致**（列表、详情、新增、修改共用同一个 VO）。

**写接口会回读一次再返回**。`createTime` / `updateTime` 由数据库的 `DEFAULT CURRENT_TIMESTAMP` 填，MyBatis-Plus 插完不会把生成的值带回实体；金额的小数位（传 `10.5` 存成 `10.50`）同理。不回读的话，POST 会返回 `createTime: null`、`amount: 10.5`，而紧接着 GET 同一个 id 却有值——一份自相矛盾的数据。金额这次数值是**相等**的，端到端跑一遍都不觉得哪里不对，所以断言要看 JSON 原文。

**找不到、或存在但属于别人，一律 `404`（不是 `403`）**。主键连续自增，`403` 等于确认该 id 存在，就成了存在性探测点。

### GET `/api/expense/summary/category?startDate=&endDate=`

按分类汇总，给饼图。日期参数可选，**不传即全部时间**（不是"本月"——默认区间是前端的事）。

**出参** `data`

```json
[
  { "category": "餐饮", "amount": 1200.50 },
  { "category": "交通", "amount": 300.00 }
]
```

**只含有记录的**分类，**不补零**，按金额降序。没有记录时返回空数组。

> 不补零是有意的：补了会让饼图多出几块永远为 0 的扇区，图例被撑长，真正花过钱的分类反而挤在一起看不清。这一点与下面的按月汇总**恰好相反**。

**这个接口不收 `category` 参数**，所以列表上的分类筛选**不影响饼图**。饼图回答的是"这段时间的钱花在哪些分类上"，筛成单一分类后它就只剩一块、没有信息量了。前端把当前区间写在卡片上，让这个联动看得见。

### GET `/api/expense/summary/month?year=2026`

按月汇总，给折线图。`year` 可选，不传即当前年份（按后端的"今天"口径）。合法范围 `1900..9999`，超出返回 `400`。

**出参** `data`

```json
[
  { "month": "2026-01", "amount": 1500.00 },
  { "month": "2026-02", "amount": 980.50 }
]
```

**恒为 12 项**、按月份升序、**没有记录的月份 `amount` 为 `0.00`**（不是 `0`——同一份响应里两种金额写法就是契约上的不一致）。

> 必须补零：折线图的横轴要是完整的时间轴。只给有数据的月份，3 月会直接连到 7 月，图上看着像"稳步增长"，而实际中间四个月一分没花。补零由后端做，前端不要再自己拼月份。

**实现**：`select MONTH(expense_date), SUM(amount) ... GROUP BY MONTH(expense_date)`，区间取该年 1 月 1 日至 12 月 31 日，索引 `(user_id, expense_date)` 可覆盖。用 `MONTH()` 而不是 `DATE_FORMAT(..., '%Y-%m')`：年份已由入参定死，SQL 里没必要再拼一次前缀再去截字符串；顺带这段 wrapper 里不含任何字面量（引号、`%`），而 MyBatis-Plus 对传进 wrapper 的字符串是做注入检查的。12 个月的名字由 Java 补全。

### 预置分类（已确认）

`餐饮` / `交通` / `购物` / `娱乐` / `医疗` / `其他`

**校验**：新增和修改时，后端校验 `category` 必须在这个范围内（**trim 之后**比对），非法值返回 `400`，错误提示里会列出当前全部合法值。

**这份清单在前端也有一份**（`src/types/expense.ts` 的 `EXPENSE_CATEGORIES`），是刻意的重复：这里没有"取分类列表"的端点，为一个六项、几乎不变、又要拿来做下拉选项的清单新增接口不划算。代价是两处要一起改——所以也**没有**把清单塞进任何响应里做隐式同步：不一致时至少能在提交时撞上一个 `400`，而不是两边各自安好地跑下去。

**只 trim，不做别的宽容**：`餐饮 ` 先被 trim 成 `餐饮` 再校验，所以它合法、且存进库的就是 `餐饮` ——库里不会同时出现看起来一样的两个分类（那会让按分类汇总裂成两行）。

trim 用的是 `String.trim()` 的口径，只去 **ASCII 空白**：`餐饮　`（**全角空格**）不会被去掉，于是校验不通过、返回 `400`。全角空格在中文输入法下很容易顺手打出来，这是**已知的边界**。它不是漏洞——那一笔存不进去，库里不会多出一行——但提示里列的是合法分类名，用户未必看得出差别在空格上。

### 汇总一律在后端做

前端**不要**把列表里的金额加起来显示。`summaryByCategory` 与 `sumOf`（首页今日消费用的那个）在实现上就是同一段路径——`sumOf` 是把分组结果加起来的，不另写一条汇总 SQL。两条路径各写一遍，就等于"哪些行该被算进来"有了两份判断，将来只给其中一侧加了条件，两边给出的合计数就会不一样——差几毛钱没有人会当成 bug 报上来。

### 数据隔离

`wb_expense` 带 `user_id`，隔离由 MyBatis-Plus 的租户插件在 SQL 生成阶段注入，业务代码里**不写** `user_id` 条件。上面 §9 里 `category` 汇总那条的 WHERE 只有日期条件、`/api/dashboard` 里 `sumOf` 那条更是连分类都不分——这类"代码里看不见条件"的路径在本仓库一律单独钉用例，见 CLAUDE.md 的测试一节。

### GET `/api/course?semesterId=1`

**出参** `data`：课程数组（**不分页**，一个学期的课就几十条）

```json
[
  {
    "id": 1, "semesterId": 1, "name": "高等数学", "teacher": "李老师", "location": "教三 201",
    "dayOfWeek": 1, "startSection": 2, "endSection": 3,
    "startWeek": 1, "endWeek": 18, "weekType": 0
  }
]
```

### 回显约定（前后端必须一致）

- 节次 `1-6`，时段划分：**早晨(1) / 上午(2-3) / 下午(4-5) / 晚上(6)**
- **时段名称由前端根据节次推导**，接口不返回
- 具体每节几点几分也由前端决定，接口不返回
- `weekType`：`0` 每周 / `1` 单周 / `2` 双周

## 12. 已确认事项

**1. 删除学期时，其下课程的处理 —— 采用 B 方案：禁止删除**

有课程关联时，`DELETE /api/semester/{id}` 返回 `400`，`msg` 提示"请先删除该学期下的课程"。

**选择理由**：学期是低频操作，多一步确认成本很低；而级联删除一旦误操作，用户的课程数据不可逆丢失。

**2. 注册开关 —— 加**

配置项 `workbench.registration.enabled`，默认 `true`。关闭后 `POST /api/auth/register` 返回 `403`。

**理由**：定位是"主要自己用，顺便让别人用"。默认开放，需要时改配置关掉即可，不必改代码。
