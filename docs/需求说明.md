## 1. 项目定位

**一句话：** 一个面向个人的在线工作台，用户登录后拥有独立空间，把日常高频使用的几类信息集中在一处管理。

**形态：** Web 网站，部署后可公开访问。用户在浏览器中登录，进入自己的工作台。

**与普通待办 App 的区别：** 不是单点工具，而是把「每日计划 + 生日提醒 + 课程表 + 备忘 + 资讯 + 记账」聚合到一个入口。

---

## 2. 目标用户

| 项 | 说明 |
|---|---|
| 用户画像 | 需要一个地方集中管理个人日常事务的人（学生、职场人均可） |
| 使用方式 | 浏览器访问，登录后进入个人工作台 |
| 用户规模 | 多用户，**每个用户的数据互相隔离、互不可见** |
| 认证方式 | **账号密码登录**（QQ 登录延后，见 §3.0） |

## 3. 功能模块

### 3.0 账号与登录【基础能力】

> 这是所有模块的前提，没有它其余模块都无法落地。

**用户故事**

- 作为访客，我要能注册账号，以便拥有自己的工作台
- 作为用户，我要能登录/登出，以便在不同设备上访问自己的数据
- 作为用户，我要保证**我的数据只有我能看到**，别人登录后看不到我的任何内容

**关键点**

- 所有业务表都必须带用户标识，任何查询都必须限定当前用户
- 这是**安全底线**，不是可选项：漏一条查询条件，就是数据泄露
- 密码必须**加盐哈希**存储（BCrypt），禁止明文或 MD5

**关于 QQ 登录（已决定延后）**

QQ 互联（<https://connect.qq.com>）申请应用时要求**网站域名已完成 ICP 备案**，个人开发者通常难以满足。

**决定：第一版只做账号密码登录，QQ 登录等备案条件具备后再作为增强加入。**
这不影响架构 —— 两种方式最终都是"登录后拿 token"，见 §5。

**优先级建议**：P0

### 3.1 每日计划

> 定位：**每日任务清单**。用户添加具体的任务，完成后手动勾选。
> 与「日历」（只管生日）职责完全分开。

**用户故事**

- 作为用户，我要能添加当天的任务（如「喝水量」「刷题」「拿快递」），以便知道今天要做什么
- 作为用户，我要能在任务完成后**手动勾选**，以便标记已完成
- 作为用户，我要能查看**近 6 个月内**的计划，以便回顾做过什么

**关键点**

- 任务的核心交互是**勾选完成**（复选框式），不是复杂的时间安排
- 可见范围：**6 个月内**

**已确认**

- 任务**纯打勾**完成，**不记录数量**（不做"8 杯里喝了几杯"这类进度）
- **不引入任务模板**，每天手动添加任务 —— 表结构因此保持简单

**优先级建议**：P0

---

### 3.2 日历 —— 生日与纪念日

> **本模块范围已收窄**：不再记录普通日程事件，**只记录生日/纪念日**。
> 原「日历事件」相关的重复规则、跨天事件等复杂度**全部取消**。

**用户故事**

- 作为用户，我要能添加**自己、家人、朋友**的生日，以便不忘记
- 作为用户，我要能添加纪念日，以便记录重要日子
- 作为用户，我要在**生日快到时在页面上看到提前提示**，以便来得及准备
- 作为用户，我要能查看所有已录入的生日列表，以便管理

**关键点**

- 记录对象是**人**（自己 / 家人 / 朋友），需要姓名 + 关系 + 日期
- 生日是**每年重复**的，按"月-日"计算，不存具体年份（除非要显示年龄）
- **页面提前提示**：进入工作台首页时，检查是否有临近的生日并展示
- **提醒天数**：**默认提前 7 天**，每条可单独设置为 **1～7 天**
- **只支持公历**，不做农历换算，不引入农历依赖库

**优先级建议**：P0

### 3.3 课程表

**用户故事**

- 作为学生用户，我要能录入课程（名称、时间、地点、老师），以便生成我的课表
- 作为学生用户，我要能按周查看课表，以便知道今天上什么课

**关键点**

- 课表是**周期性**的（每周重复），且通常有**学期**概念（起始周、总周数）
- 是否需要支持"单双周"、连堂课 —— 待确认
- **已确认需要此模块**（不是可选功能）

**优先级建议**：P1

### 3.4 备忘录

**用户故事**

- 作为用户，我要能创建/编辑/删除备忘，以便记录较长内容
- 作为用户，我要能搜索备忘录，以便快速找到

**关键点**

- 是否需要富文本编辑、标签分类 —— 待确认

**优先级建议**：P0

---

### 3.5 每日新闻

> 数据源已确定：**聚合数据（juhe.cn）新闻 API**

**用户故事**

- 作为用户，我要能在工作台看到当日新闻，以便不用另开网站

**关键点 ⚠️**

- **必须服务端缓存。** 绝不能每次用户刷新都打第三方接口 —— 每个用户每刷一次页面消耗一次配额，几十个用户就会把配额耗尽。
  - 正确做法：后端定时（如每小时）拉取一次，缓存到内存/数据库，所有用户读缓存
  - **这是架构决定，不是后期优化项**
- 所有用户看**同一份**新闻（与"每人订阅不同源"相比，大幅简化）
- 需要确认聚合数据新闻接口的**当前计费方式与配额**（该平台接口档位会调整，需自行核实）

**优先级建议**：P1

---

### 3.6 每日消费

**用户故事**

- 作为用户，我要能记录一笔支出（金额、类别、备注），以便掌握花销
- 作为用户，我要能查看某月/某日的消费汇总，以便了解钱花在哪

**关键点**

- 金额字段用 `DECIMAL`，**不能用浮点数**（浮点会丢精度）
- 需要消费分类（餐饮/交通/购物…），第一版**预置常用分类**（见 §8）
- **需要图表统计**：按类别饼图、按月趋势

**优先级建议**：P1

## 4. 跨模块的共性问题

这几件事会影响所有模块的设计，建议**早定**：

1. **数据隔离的实现层次** —— 在 Service 层统一强制，还是每个 Mapper 查询手写条件？（建议前者，后者迟早漏）
2. **"某一天"的时区问题** —— 服务器时区与用户时区不一致时，"今天"是哪天？建议统一按服务器时区并写进文档
3. **日期格式统一** —— 前后端传输用 `yyyy-MM-dd HH:mm:ss` 还是时间戳，必须统一

---

## 5. 架构约定：为将来的 App 预留

**当前不做 App，但架构上按"后端是独立 API 服务"来做**，这样将来加 App 是增量工作而非推倒重来。

| 约定 | 原因 |
|---|---|
| 后端只提供**纯 REST API**，不做服务端渲染 | App 无法消费 HTML |
| 认证用 **token**，不用浏览器 session cookie | cookie 绑定浏览器，App 用不了 |
| 业务逻辑全部在 Service 层，不依赖 Web 层特性 | 保证 API 可被任意客户端调用 |

有了这三条，将来用 uni-app / Capacitor 套壳即可复用现有前端，成本远低于重写原生 App。

> 每日计划 = 纯打勾任务清单、不用模板、可查 6 个月内 ·

以下问题**不阻塞开始设计**。我会先按默认取值推进，你随时可以推翻：

| # | 问题 | 我将采用的默认取值 | 理由 |
|---|---|---|---|
| 1 | 「6 个月」是查看范围还是数据保留策略？ | **查看范围限制，不删数据** | 更安全，误删用户数据不可逆 |
| 2 | 「纪念日」和「生日」是否同一套结构？ | **同一张表**，用 `type` 字段区分 | 字段几乎一致，拆两张表是重复 |
| 3 | 是否显示生日倒计时？ | **显示**（"还有 3 天"） | 成本低，体验提升明显 |
| 4 | 消费分类预置还是自定义？ | **预置常用分类** | 第一版不做自定义，省一个管理界面 |
| 5 | 新闻条数与分类？ | **默认 20 条、不分类** | 先跑通链路 |
| 6 | 聚合数据接口的计费与配额？ | **需你自行确认** | 我无法查证；但无论哪种计费，都必须服务端缓存（§3.5） |
| 7 | 大概多少人用？ | 按**几十人**设计 | 不做额外性能优化，够用即可 |
| 8 | 部署到哪里？ | **暂缓，软件完成后再定**（倾向 Oracle 永久免费） | 架构可移植，见下方约束 |

**部署推迟的前提约束**（违反任何一条，将来换部署地点都要改代码）：

- 不硬编码域名 / IP / 端口，全部走环境变量或配置文件
- 不把上传文件存本地磁盘（应存对象存储，或至少保证可迁移）
- 不把云厂商专有 SDK 写进业务逻辑
- 后端保持纯 REST API（见 §5）

> ⚠️ 选 Oracle 永久免费需注意的现实问题：对中国用户注册不友好（需国际信用卡验证）、
> ARM 实例常因容量不足抢不到、长期闲置的实例可能被回收。**建议软件做完再评估**，
> 届时若不可行，退回香港轻量服务器即可，代码不用改。
