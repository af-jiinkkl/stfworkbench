## 2. 请求参数

| 参数 | 必填 | 本项目是否使用 | 说明 | 实测取值（2026-10-04） |
|---|---|---|---|---|
| `key` | 是 | ✅ 用 | appkey，见 §7 | 环境变量 `JUHE_NEWS_KEY` |
| `type` | 否 | ✅ 用（写死 `top`） | 新闻分类 | 本项目只取 `top`（头条推荐）。**实测：不传 `type` 也返回同一批数据**（接口自带默认分类），但本项目仍显式传 `top` |
| `page` | 否 | ❌ 没用 | 页码 | 未实测 |
| `page_size` | 否 | ❌ 没用 | 每页条数 | **实测有效**：传 `page_size=5` 返回 5 条；**不传时默认 30 条** |
| `is_filter` | 否 | ❌ 没用 | 是否过滤 | 未实测 |
| `word` | 否 | ❌ 没用 | 搜索关键词 | 未实测 |

> 本项目**不分类抓取**（只 `type=top`），且**不传 `page_size`** —— 于是拿的是接口默认的
> **30 条/次**。这是 `需求说明.md` §8 问题 5 定下的默认取值：要防的是抓取的**次数**
> （见 §6），条数省不出配额，所以 `page` / `page_size` 这两个参数虽然接口支持，本项目没传。
>
> 注：原文档写的"条数不截断、接口返回多少就存多少"，实现上等价于"不传 `page_size`"，
> 而**接口那一侧仍有个 30 条的默认值** —— 这两句不冲突，但要知道 30 是接口给的、不是本项目设的。

**本项目实际发出的请求**：

```
GET https://v.juhe.cn/toutiao/index?type=top&key=<appkey>
```

不带任何超时重试、不带分页 —— 一次请求拿一整批。连接超时 5 秒、读取超时 10 秒
（`JuheNewsSourceClient` 构造函数里写死；抓取跑在定时任务线程上，没有超时会把线程挂死）。

## 3. 响应结构

> 下面这份是**结构示例**（字段名与嵌套关系取自本项目已实测的响应），
> 具体字段是否齐全、是否还有别的字段，请以官方文档为准（**待补**）。

```json
{
  "reason": "成功的返回",
  "error_code": 0,
  "result": {
    "stat": "1",
    "data": [
      {
        "title": "新闻标题",
        "date": "2026-09-21 08:00:00",
        "author_name": "来源媒体名",
        "url": "https://...",
        "uniquekey": "……",
        "category": "头条"
      }
    ]
  }
}
```

### 顶层字段

| 字段 | 类型 | 本项目怎么处理 |
|---|---|---|
| `error_code` | int | **成败的唯一依据**：`!= 0` 即失败（详见 §4） |
| `reason` | string | 失败时把原因拼进异常消息 |
| `resultcode` | string | ❌ 未使用 —— 旧式的字符串状态码。**成功响应里不出现，出错时才带**（如 `"101"`）。本项目只认数值型的 `error_code` |
| `result.stat` | string | 未使用 |
| `result.data` | array \| **null** | 新闻条目数组；**可能是 null**，见下 |

> ⚠️ **`result.data` 为 null 是正常情况**（接口正常、那个时段就是没有内容），
> 要当**空列表**处理，不能当异常 —— "抓取失败"（抛异常、跳过本轮）与"这次没有新闻"
> （正常，什么都不写）是两件事，混成一件会让空内容的日志一直报错。

### `result.data[]` 条目字段

| 字段 | 类型 | 本项目怎么用 | 缺失时的行为 |
|---|---|---|---|
| `title` | string | 新闻标题，**空则丢弃该条** | 丢弃（无标题的条目在界面上是一行空白，点也点不动） |
| `date` | string | 发布时间，用于排序 | 解析不了 → 该条**保留**、按 `null` 处理、排序排最后 |
| `author_name` | string | 来源 | 空串 |
| `url` | string | 原文链接 | 空串（前端渲染成不可点的 `<span>`，不是空 `href`） |
| `uniquekey` | string | ❌ 未使用 | — |
| `category` | string | ❌ 未使用（实测值为 `"头条"`） | — |
| `thumbnail_pic_s` | string | ❌ 未使用（缩略图 URL） | — |
| `is_content` | string | ❌ 未使用 | — |

> 实测（2026-10-04）这条接口每条新闻返回 **8 个字段**：`uniquekey` / `title` / `date` /
> `category` / `author_name` / `url` / `thumbnail_pic_s` / `is_content`。本项目只落库其中 **4 个**
> （`title` / `date` / `author_name` / `url`）—— 缩略图与 `is_content` 在 `wb_news` 表里
> 没有对应列，属于**有意不存**，不是漏了。

**`date` 支持两种写法**，依次尝试：

1. `yyyy-MM-dd HH:mm:ss`（带时分秒）
2. `yyyy-MM-dd`（第三方偶尔只给到日期，按当天 00:00:00 处理）

两种都解析不了 → 记为 `null`，**不抛异常**（这一条时间格式怪，不代表整批新闻都不要了；
标题和链接都在，点开就能看，无非是排序时排在最后）。

## 4. 如何判定"这次抓取失败了"

这是本项目在这一接口上最容易踩的坑，**已实测**：

> **成败必须看 body 里的 `error_code`，不能看 HTTP 状态码。**
> 接口业务失败时**照样回 HTTP 200**，只是 body 里 `error_code` 非 0
> （appkey 失效、超出配额都走这条路）。

只认状态码的话，一次失败的抓取会被记成"成功 0 条"，真正的失败原因一直在 body 里没人看
—— 表现是当天新闻一直是空的，而日志里一条错都没有。

代码里的判定顺序（`JuheNewsSourceClient#parse`）：

| 情况 | 判定 | 处理 |
|---|---|---|
| `error_code` 缺失 | 按 `-1` 当失败 | 抛业务异常（报文形状变了就是不该当成成功） |
| `error_code != 0` | 失败 | 抛业务异常，消息里带 `reason` 与 `code` |
| `result.data` 为 null / 缺失 / 非数组 | **正常，空列表** | 返回空列表，不写库、不报错 |
| 响应不是 JSON（如 HTML 错误页） | 失败 | 异常里带**响应前 200 字**，便于复现 |

### 错误码表（**待补**）

下面只列了代码会分支的那一类，其余请从官方文档补全：

| `error_code` | `resultcode` | `reason` 含义 | 本项目表现 | 排查方向 |
|---|---|---|---|---|
| `0` | （无） | `success!` | 正常入库 | — |
| `10001` | `"101"` | **错误的请求 KEY** | 抛业务异常，跳过本轮抓取 | `JUHE_NEWS_KEY` 配错 / 失效 |
| 其余非 0 | — | **待补**（配额耗尽、无权限、余额不足等） | 同上 | 见 §7 核对 appkey / 配额 |

**实测记录（2026-10-04）**：拿一个无效 key 打接口，返回的是

```
HTTP 200
{"resultcode":"101","reason":"错误的请求KEY","result":null,"error_code":10001}
```

两条要点，都与"只看 HTTP 状态码"的直觉相反：

1. **失败照样回 HTTP 200** —— 只有 `error_code` 非 0 才说明失败
2. **失败时 `result` 是 `null`** —— 所以代码里必须**先判 `error_code` 再取 `result.data`**，
   顺序反了会在正确失败的情况下抛空指针（`JuheNewsSourceClient#parse` 正是这个顺序）

## 6. 配额与计费

> **接口本身不告诉你配额。** 实测（2026-10-04）：响应头只有 `Date` / `Content-Type` /
> `Transfer-Encoding` / `Connection` / `Set-Cookie` / `Etag`，**没有**任何
> `X-RateLimit-*` 之类的剩余次数信息；响应体里也没有。要查额度只能登录
> **聚合数据控制台**看该接口的用量。
>
> 这条本身就是设计依据 —— 后端**不能**靠响应头去自适应降频，只能按已知额度保守地定抓取周期。

仍需在控制台/官方文档确认（**待补**）：

- 免费额度是多少？按天还是按月？
- 单次调用消耗多少？
- 超出后是拒绝（`error_code` 非 0）还是扣费？
- 是否有并发限制？

> 为什么这条最要紧：`需求说明.md` §3.5 明确写了「**必须服务端缓存**」——
> 绝不能每次用户刷新都打第三方接口，否则几十个用户就会把配额耗尽。
> 本项目的做法是**后端定时抓取一次、所有用户读缓存**（`NewsFetchJob`），
> `/api/news` 是**只读**的、**没有"立即刷新"按钮** —— 那按钮就是个人人可点的配额放大器。

### 本项目的抓取频率

| 配置 | 默认值 | 说明 |
|---|---|---|
| `JUHE_NEWS_CRON` | `0 7 * * * *`（每小时第 7 分钟） | Spring 六段式 cron。**刻意避开整点** —— 整点是各家定时任务扎堆的时刻 |

即：**默认每天最多 24 次请求**。一天下来消耗的配额 = 24 × 单次消耗（§1 待补）。

抓取**幂等**：靠 `(fetch_date, title)` 当天去重（`NewsServiceImpl#refresh` 的
`existingTitlesOn`），cron 一小时跑一次不会把同一条新闻写 24 遍。

## 7. 本地怎么配置与验证

### 配置（appkey 不入库）

真实 appkey 通过环境变量提供，代码读的是 `workbench.news.appkey`
（`application.yml:56` 的 `${JUHE_NEWS_KEY:}`）。三种放法，任选：

| 方式 | 命令 / 位置 | 是否入库 | 说明 |
|---|---|---|---|
| Windows 用户级环境变量（推荐） | `setx JUHE_NEWS_KEY "<你的key>"` | 否 | 设完要**重开终端 / 重启 IDE** 才生效 |
| 当前会话临时 | Git Bash：`export JUHE_NEWS_KEY=<key>` | 否 | 关掉窗口就没了 |
| IDE 运行配置 | Run Configuration 的 Environment variables | 否 | 每次启动后端都带上 |

> **不要**写进 `application.yml` 或任何提交进 git 的文件。
> 若确实想留一份本地记录，请放在 `.env.local`（已被根级 `.gitignore` 忽略）
> 或 git 之外的位置 —— 需要我帮你建这么一份，说一声。

### 验证是否生效

1. 后端带 `JUHE_NEWS_KEY` 启动（**改完必须重启**，别对着旧进程验证）
2. 把抓取周期临时调快，别对着默认的每小时干等：

   ```bash
   export JUHE_NEWS_CRON='*/15 * * * * *'   # 每 15 秒跑一次
   ```

3. 看日志里有没有 `scheduling-1` 线程上的记录
4. 查库确认：

   ```sql
   SELECT id, fetch_date, title, publish_time FROM stfworkbench.wb_news ORDER BY id DESC LIMIT 10;
   ```

> **未配置 appkey 时不影响启动**，只是每轮抓取记一条 **DEBUG** 后跳过
> —— 默认日志级别下看不见，别把"没配 key"误判成"抓取坏了"。
> 这与 `JWT_SECRET` 缺了即启动失败**刻意相反**：JWT 没有安全默认值可取，
> 而新闻源没配就是没配，登进去少一张卡片远比服务起不来合适。

## 8. 本项目消费它的三条刻意写法

记录在 `JuheNewsSourceClient` 的类注释里，改这个类之前先读一遍：

1. **按 `error_code` 判成败，不只看 HTTP 状态** —— 理由见 §4。
2. **取 `byte[]` 再自己按 UTF-8 解，不交给框架按响应头解** —— 新闻是中文，
   对方响应头的 charset 不一定靠得住；一旦它声明 ISO-8859-1，整批标题会变乱码，
   而乱码看着像"数据源质量差"，不像一个能修的 bug。
3. **不复用应用那套 Jackson 配置** —— `JacksonConfig` 定制过日期格式与时区，
   那是**本项目的**对外契约；拿它去解第三方报文，会让第三方的字段格式被本方配置影响，
   将来改自己的日期格式就会悄悄改到这里的行为。

另有一处与本接口无关但同属新闻模块：超长的三个字段（标题/来源/链接）**截断而不是丢弃整条**
（`NewsServiceImpl#clip`，宽度抄 `schema.sql`）—— MySQL 严格模式下超长会让整条 INSERT 失败，
为一条标题长的新闻把同批另外几十条一起丢掉最不划算。
