## 2. 全局约定

遵循 `CLAUDE.md` 的 MySQL 规范：

- 引擎 `InnoDB`，字符集 `utf8mb4`，排序 `utf8mb4_general_ci`
- 主键 `id` 自增；必带 `create_time`、`update_time`、`deleted`
- 表名前缀统一 `wb_`

### 2.1 逻辑删除（B 方案）

**`deleted` 用 `BIGINT`，不是 `TINYINT`。**

| 值 | 含义 |
|---|---|
| `0` | 未删除 |
| 非 0 | 删除时刻的时间戳 |

**为什么不用 0/1？**

因为 `wb_user.username` 上有唯一索引。如果 `deleted` 是 0/1，用户注销后那行数据还在、唯一索引仍然拦着，**这个用户名永远无法再被注册**。

改存时间戳后，同一个用户名被删两次会得到两个不同的时间戳，配合组合唯一索引 `(username, deleted)` 就不会冲突，用户名可以复用。

**所有业务查询都必须带 `deleted = 0` 条件。**

> ⚠️ 实现提示：MyBatis-Plus 的逻辑删除要配 `@TableLogic(value = "0", delval = "UNIX_TIMESTAMP()")`。
> 秒级时间戳意味着**同一秒内删两次同名用户**才会冲突——实际不可能发生，可以接受。

### 2.2 ⚠️ 安全铁律

**所有带 `user_id` 的表，任何查询都必须限定当前用户。** 漏一个条件就是数据泄露——别人能看到你的备忘录和消费记录。

实现方式（二选一，我会用第一种）：
1. **MyBatis-Plus 拦截器统一注入 `user_id` 条件** —— 推荐，从机制上防漏
2. 每个 Mapper 手写条件 —— 迟早会漏

## 4. 逐表设计

### 4.1 `wb_user` 用户表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | 主键 |
| `username` | VARCHAR(50) | NOT NULL | 登录名 |
| `password` | VARCHAR(100) | NOT NULL | **BCrypt 哈希**，禁止明文/MD5 |
| `nickname` | VARCHAR(50) | NOT NULL, 默认 `''` | 昵称 |
| `avatar` | VARCHAR(500) | NOT NULL, 默认 `''` | 头像地址 |
| `qq_openid` | VARCHAR(64) | NULL | QQ 登录标识，**预留**，暂不使用 |
| `create_time` / `update_time` / `deleted` | | | 通用字段 |

**唯一索引**：`uk_username (username, deleted)` —— **组合索引**，不是单独 `username`（见 §2.1）

**说明**：BCrypt 哈希固定 60 字符，字段留 100 是余量。`qq_openid` 现在就加上，将来接 QQ 登录不用改表。

---

### 4.2 `wb_plan_task` 每日计划任务

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `user_id` | BIGINT | NOT NULL | 所属用户 |
| `plan_date` | DATE | NOT NULL | 归属日期（哪一天的） |
| `content` | VARCHAR(255) | NOT NULL | 任务内容，如"拿快递" |
| `completed` | TINYINT | NOT NULL, 默认 0 | 0 未完成 / 1 已完成 |
| `completed_time` | DATETIME | NULL | 完成时间 |
| `sort_order` | INT | NOT NULL, 默认 0 | 排序值 |
| 通用字段 | | | |

**索引**：`idx_user_date (user_id, plan_date)`

**说明**

- 按需求**不做任务模板**，每条任务都是手动添加的独立记录
- **不记录数量**，纯勾选（`completed` 就是布尔）
- "查看 6 个月内"是**查询范围限制**，数据不删（见需求 §8）
- 索引 `(user_id, plan_date)` 正好覆盖"查某人某天的任务"和"查某人某段日期"两种查询

### 4.3 `wb_anniversary` 生日与纪念日

> 生日和纪念日**共用一张表**，用 `type` 区分——两者字段几乎一致，拆两张是重复。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `user_id` | BIGINT | NOT NULL | 所属用户 |
| `name` | VARCHAR(50) | NOT NULL | 姓名（生日）或名称（纪念日） |
| `type` | TINYINT | NOT NULL | 1 生日 / 2 纪念日 |
| `relation` | VARCHAR(20) | NOT NULL, 默认 `''` | 自己 / 家人 / 朋友 |
| `month` | TINYINT | NOT NULL | 月 1-12 |
| `day` | TINYINT | NOT NULL | 日 1-31 |
| `remind_days` | TINYINT | NOT NULL, 默认 7 | 提前提醒天数 **1-7** |
| `remark` | VARCHAR(255) | NOT NULL, 默认 `''` | 备注 |
| 通用字段 | | | |

**索引**：`idx_user (user_id)`

**关键设计：为什么只存 `month` + `day`，不存完整日期？**

因为生日/纪念日是**每年重复**的，年份没有意义。这样存的好处是"查未来 N 天内的生日"逻辑清晰。

**代价**：跨年计算（比如今天是 12 月 30 日，下个月 1 月 5 日的生日）不能在 SQL 里简单比较。

**我的处理**：一个人的生日记录通常只有几十条，直接**全部取出来在 Java 里算**，不做复杂 SQL。这个规模下完全没问题。

**注意**：如果将来要显示年龄或"第几年"，需要补 `year` 字段。现在不加，避免猜测。

### 4.4 `wb_memo` 备忘录

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `user_id` | BIGINT | NOT NULL | 所属用户 |
| `title` | VARCHAR(100) | NOT NULL, 默认 `''` | 标题 |
| `content` | TEXT | NULL | 正文 |
| 通用字段 | | | |

**索引**：`idx_user (user_id)`

**说明**

- 正文用 `TEXT`。`CLAUDE.md` 说"避免 text 滥用"，但备忘录正文确实可能很长，这里是合理使用
- **搜索**：第一版用 `LIKE '%关键词%'`。这个查询用不上索引，但几十个用户、每人几百条备忘录的规模下无所谓，**不做过早优化**

### 4.5 `wb_news` 新闻缓存【v0.2】

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `title` | VARCHAR(255) | NOT NULL | 标题 |
| `source` | VARCHAR(50) | NOT NULL, 默认 `''` | 来源 |
| `url` | VARCHAR(500) | NOT NULL, 默认 `''` | 原文链接 |
| `publish_time` | DATETIME | NULL | 发布时间 |
| `fetch_date` | DATE | NOT NULL | 抓取日期 |
| `create_time` | DATETIME | NOT NULL | |

**索引**：`idx_fetch_date (fetch_date)`

**⚠️ 这是全局共享的缓存表，没有 `user_id`，也不带 `update_time` / `deleted`。**

所有用户看同一份新闻（需求 §3.5），由**后端定时任务**从聚合数据拉取后写入。**绝不能每次用户刷新就去打第三方接口**——配额会秒光。

这是本项目里**唯一一张不遵循"通用字段"规范的表**，因为它是缓存不是业务数据，加逻辑删除没有意义。**已确认此例外。**

---

### 4.6 `wb_expense` 消费记录【v0.2】

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `user_id` | BIGINT | NOT NULL | 所属用户 |
| `amount` | DECIMAL(10,2) | NOT NULL | 金额（元） |
| `category` | VARCHAR(20) | NOT NULL | 消费分类 |
| `expense_date` | DATE | NOT NULL | 消费日期 |
| `remark` | VARCHAR(255) | NOT NULL, 默认 `''` | 备注 |
| 通用字段 | | | |

**索引**：`idx_user_date (user_id, expense_date)`

**说明**

- 金额用 `DECIMAL(10,2)`，**绝不能用 `FLOAT`/`DOUBLE`**——浮点数存钱会丢精度（`0.1 + 0.2 ≠ 0.3`），这是经典事故
- `10,2` 表示最多 10 位、其中 2 位小数，即最大 `99,999,999.99`，够用
- 分类第一版**预置**，用 `VARCHAR` 存分类名。将来要自定义分类时再抽成独立表
- 图表统计（按分类饼图、按月趋势）靠 `GROUP BY category` 和 `GROUP BY DATE_FORMAT(expense_date,'%Y-%m')`，索引 `(user_id, expense_date)` 能覆盖

---

### 4.7 `wb_semester` 学期【v0.3】

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `user_id` | BIGINT | NOT NULL | 所属用户 |
| `name` | VARCHAR(50) | NOT NULL | 学期名称，如"2026 春季学期" |
| `start_date` | DATE | NOT NULL | **第 1 周的周一** |
| `total_weeks` | TINYINT | NOT NULL | 总周数，如 20 |
| 通用字段 | | | |

**索引**：`idx_user (user_id)`

**注意**：`start_date` 必须约定为**第 1 周的周一**。有此基准才能把"第 N 周 + 星期几"换算成真实日期。这个约定要写进接口文档，前端也得知道。

### 4.8 `wb_course` 课程【v0.3】

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK, 自增 | |
| `user_id` | BIGINT | NOT NULL | 所属用户 |
| `semester_id` | BIGINT | NOT NULL | 所属学期 |
| `name` | VARCHAR(50) | NOT NULL | 课程名 |
| `teacher` | VARCHAR(50) | NOT NULL, 默认 `''` | 任课老师 |
| `location` | VARCHAR(50) | NOT NULL, 默认 `''` | 上课地点 |
| `day_of_week` | TINYINT | NOT NULL | 星期几 **1-7** |
| `start_section` | TINYINT | NOT NULL | 开始节次 **1-6** |
| `end_section` | TINYINT | NOT NULL | 结束节次 **1-6** |
| `start_week` | TINYINT | NOT NULL | 起始周 |
| `end_week` | TINYINT | NOT NULL | 结束周 |
| `week_type` | TINYINT | NOT NULL, 默认 0 | 0 每周 / 1 单周 / 2 双周 |
| 通用字段 | | | |

**索引**：`idx_user_semester (user_id, semester_id)`

**节次约定（重要）**

**一天 6 节**，划分如下：

| 节次 | 时段 |
|---|---|
| 1 | 早晨 |
| 2-3 | 上午 |
| 4-5 | 下午 |
| 6 | 晚上 |

- 时段归属（上午/下午/晚上）**由前端根据节次推导**，数据库不存，避免冗余
- 具体每节几点几分也由**前端**决定显示，数据库不存时间点
- 一门课在课表上可能占多个格子（如周一 1-2 节、周三 3-4 节），那就在表里存**多条记录**，不设计"多时段"字段

**`week_type` 说明**：需求里单双周标着"待确认"，但加一个 `TINYINT` 几乎零成本，将来再加要改表、改接口、改前端三处，所以先加上。

## 5. 完整 DDL

```sql
-- 用户表
CREATE TABLE `wb_user` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `username`    VARCHAR(50)  NOT NULL                COMMENT '登录名',
  `password`    VARCHAR(100) NOT NULL                COMMENT '密码（BCrypt 哈希）',
  `nickname`    VARCHAR(50)  NOT NULL DEFAULT ''     COMMENT '昵称',
  `avatar`      VARCHAR(500) NOT NULL DEFAULT ''     COMMENT '头像地址',
  `qq_openid`   VARCHAR(64)  NULL                    COMMENT 'QQ 登录标识（预留）',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP                COMMENT '创建时间',
  `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted`     BIGINT       NOT NULL DEFAULT 0      COMMENT '逻辑删除：0 未删除，非 0 为删除时间戳',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`, `deleted`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='用户表';

-- 每日计划任务
CREATE TABLE `wb_plan_task` (
  `id`             BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',

  `plan_date`      DATE         NOT NULL                COMMENT '计划日期',
  `content`        VARCHAR(255) NOT NULL                COMMENT '任务内容',
  `completed`      TINYINT      NOT NULL DEFAULT 0      COMMENT '是否完成：0 否，1 是',
  `completed_time` DATETIME     NULL                    COMMENT '完成时间',
  `sort_order`     INT          NOT NULL DEFAULT 0      COMMENT '排序值',
  `create_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP                COMMENT '创建时间',
  `update_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted`        BIGINT       NOT NULL DEFAULT 0      COMMENT '逻辑删除：0 未删除，非 0 为删除时间戳',
  PRIMARY KEY (`id`),
  KEY `idx_user_date` (`user_id`, `plan_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='每日计划任务';

-- 生日与纪念日

  `remark`      VARCHAR(255) NOT NULL DEFAULT ''     COMMENT '备注',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP                COMMENT '创建时间',
  `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted`     BIGINT       NOT NULL DEFAULT 0      COMMENT '逻辑删除：0 未删除，非 0 为删除时间戳',

  `update_time`   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted`       BIGINT      NOT NULL DEFAULT 0      COMMENT '逻辑删除：0 未删除，非 0 为删除时间戳',
  PRIMARY KEY (`id`),
  KEY `idx_user_semester` (`user_id`, `semester_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='课程';
```
